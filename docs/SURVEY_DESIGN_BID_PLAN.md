## 2. 产品目标和边界

在 EngiSpace 首页启用「投标文件」，与「设计说明」并列。支持勘察、设计、勘察设计联合三种编制类型。勘察设计联合业务不等于联合体投标；是否联合体、成员和分工另设字段。

基本流程：新建投标项目 → 导入招标文件/补遗 → 核对要求 → 关联企业资料 → 编排目录及正文 → 响应检查 → 导出可编辑 DOCX。

首个可用版本覆盖技术标、商务资信资料的编制与缺项清单、人工填写的报价信息。具体工程门类和地区尚未确定，不把房建、市政或某一省份规则写成通用规则。没有真实样本时用明确标识的脱敏合成样本验证流程，专业适用性保持待核定。

交付到 DOCX；Word/WPS 继续编辑由用户完成。签章、加密、电子交易平台提交及专业审核由用户按项目要求完成。标书不导入 CAD，不增加 CAD 连接。

不在首版范围：施工组织设计、施工报价/算量引擎、自动签章投标、自动报价决策、多人云协作、标讯抓取、插件市场、AI 效果图、自动设计计算、自动编造勘察成果。工程门类扩展按后续真实业务样本安排。

| 章节工作区 | 勘察/设计/联合模板；章节顺序、段落和简单表格编辑 | 当前正文副本、对应要求、引用资料、人工修改和保存状态 |

来源定位：PDF 使用文件版本＋物理页序；DOCX 使用文件版本＋章节/段落/表格单元格定位，不编造会随 Word 分页变化的页码。数据对象和操作名称在首阶段内落成可验证的桌面内部协议。

## 4. 勘察设计内容规则

### 勘察技术部分（章节候选，不是固定强制目录）

项目理解与工作范围；已有资料和现场条件；拟采用的勘察方法与工作安排；人员设备组织；质量、安全、环境措施；进度与成果提交；与设计及现场工作的配合。勘探孔、深度、试验参数和地质结论须有明确依据或由专业人员填写，不凭项目类型生成事实。

### 设计技术部分（章节候选）

项目理解与重点难点；总体设计思路及方案比较；相关专业设计方案；专业接口协调；质量校审；进度与成果清单；投资控制建议；报批及后续服务。结构、建筑、工艺、给排水、电气、暖通等按项目范围选择，不要求所有项目都出现所有专业。

### 商务资信与报价

按招标文件需要编制投标函、授权、资格资料、人员表、业绩表、承诺及偏差说明。人员、注册证书、企业资质、业绩和金额只能来自人工填写或已核定资料。报价先做录入、单位/税率口径标注与一致性检查，不自动决定折扣率或服务费；复杂报价表保留人工定稿入口。

### 来源和审查

- 招标原文和 AI 推测分开显示；人工确认前只是候选要求，不能直接视为完整要求清单。
- 要求与响应允许多对多关系；有文字不等于满足要求，有附件也不等于资格符合。
- 缺项显示待填写/待核定；草稿允许带标记导出，已核对稿要求适用的必填项有响应和人工复核。名称不使用「保证合规」「保证中标」。
- 补遗新增版本，保留旧版；只标记受影响的要求和章节待复核，不自动覆盖人工正文。
- 规范记录编号、版本、实施/废止信息、专业、地区、来源、核定人/日期。现有规范编号索引可借鉴，但不能直接当作有效规范库。
- 招标要求与规范疑似冲突时展示两方依据并待专业核定，不用固定优先级自动作法律或专业判断。
- 参考官方《标准勘察招标文件》《标准设计招标文件》（2017 年版）组织信息，实际项目采用何种现行文本、地方要求及专业规范需逐项核验，不能仅凭本文认定合规。

官方来源：[发布通知](https://www.ndrc.gov.cn/xxgk/zcfb/tz/201709/t20170912_962555_ext.html)、[勘察标准文本](https://www.ndrc.gov.cn/xxgk/zcfb/tz/201709/W020190905503490397221.pdf)、[设计标准文本](https://www.ndrc.gov.cn/xxgk/zcfb/tz/201709/W020190905503491039808.pdf)。本轮核对发布页面及文本入口，未完成逐条现行性、地区及工程适用性核验。

## 5. 技术方案提案（批准前不实施）

沿用 Electron＋React/TypeScript＋.NET/Open XML，不引入第二套桌面运行时。

| 层次 | 拟新增或复用 | 隔离要求 |
| --- | --- | --- |
| 界面 | 新增 desktop/app/src/features/bidding；复用视觉规范和通用交互 | 保留设计说明现有行为；避免一开始整体重构 main.tsx |
| 桌面内部业务 | 标书模型、要求/响应规则、来源和校核逻辑 | 不依赖 AutoCAD SDK，不改 CAD Contracts 和布局协议 |
| 本地保存 | 独立 bids 目录、版本化 JSON、原子保存与历史恢复 | 不迁移旧 notes；备份兼容旧版；项目资料以快照引用 |
| 进程通信 | 主进程与 preload 增加有限的标书操作 | 输入校验、路径限制；不提供任意命令执行能力 |
| DOCX | 同一 .NET 工作进程新增独立标书导出操作 | 保持设计说明原操作与输出不变；标书样式单独配置 |
| 文件解析 | 首阶段 DOCX 文本/简单表格和人工摘录 | PDF/OCR 在下一阶段按样本评估；扫描件不假装解析成功 |
| AI | 第二阶段新增可选的模型适配和可恢复任务 | 编辑保存导出无需联网；AI 失败不损坏正文 |

第一阶段允许用户登记并本地保存 PDF 作为原始资料，人工录入要求；界面明确标记尚未自动解析。复杂 DOCX 中不支持的对象必须报告，不静默漏读。

第二阶段先以统一模型接口支持一个经用户选定的提供方；密钥进入系统安全存储，日志不含密钥及完整业务原文。首次发送前清楚显示提供方、发送资料范围和用途。用户仅批准本计划不构成发送业务文件到云端的授权。本地模型可作为适配选项，是否部署另行确定。

第一阶段不引入 SQLite、向量数据库、Pi Agent 或云服务。后续数据量证明确有必要时，再提出迁移/依赖方案。源码参考方式、存储方式、内部操作和导出隔离方案由本计划一次评审；已批准范围内的内部实现无需逐个询问。

## 7. 最低验收清单

1. 勘察、设计、联合各一份脱敏样本：建立项目 → 录入要求及原文定位 → 编制 → 关闭重开 → 导出，内容、顺序和表格一致。
2. 每项已确认适用要求能定位响应章节或待补材料；人工标为不适用需保存理由。
3. 缺负责人/证书/业绩不得自动造值；过期、日期不明、证书未核定分别显示；草稿不冒充已核对稿。
4. 补遗修改周期后，旧事实保留，相关章节转待复核；另一标段不受影响。
5. 并发保存、写盘失败、损坏 JSON、恢复备份、重复导出文件名均有可验证的保护结果。
6. DOCX 用 Open XML 结构校验与内容读回验证；新增富文档不能强行套用 CAD 解析器作为唯一验收。Word/WPS 可编辑性和分页由用户集中检查。
7. 原六专业设计说明的新建/编辑/保存/导出回归通过，CAD 代码不变化；桌面验收不要求 CAD 实测。
8. AI 第二阶段才测试真实提供方；模拟返回只证明异常处理，不证明内容质量。费用、耗时和识别率记录实测，不预设宣传数值。
